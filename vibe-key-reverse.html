01 — 目标

这是个什么东西

硬件叫 Vibe Key,型号 AU05:一块铝合金手持控制器,一个旋钮 + 麦克风键 + ✓ 确认键 + ✕ 取消键 + 侧边键。卖点是把 AI 编码 agent 的实时状态用灯效显示出来, 并且能一键确认/取消/语音输入。

官方软件 Ulanzi Studio 是 Qt/C++ 写的,内置一份 Node.js 运行时跑 Stream Deck 风格的插件。 它已经支持 8 种 agent:Claude Code、Codex、Gemini CLI、Cursor、Copilot CLI、Kimi、Kiro、CodeBuddy, 把各家的 hook 事件翻译成 8 个设备状态。

error 出错PostToolUseFailure · StopFailure

sleeping 休眠SessionEnd

官方链路长什么样

这条链路是逆出来的,每一段都验证过。关键收获:大部分环节是明文的, Ulanzi 自己把 ustudio-cli 的 Node 参考实现原样装到了磁盘上,协议基本等于白送。

设备暴露的 HID 接口

Usage Page用途加密
0x0001 / 0x06标准键盘 —— 默认模式的按键码走这里否

两种模式(这是整件事的关键)

  • 默认模式(官方 App 没跑):按键走标准 HID 键码,不加密、跨平台通用。
  • 自定义模式(App 发了激活命令后):按键改走 0xfffc 加密口,由 App 查配置后 用 CGEvent 注入真正的快捷键。

这条决定了方案走向。 ✕ 和侧边键在默认模式下完全不发东西——它们只在自定义模式的加密口上报。 所以「全键可编程 + 灯效显示」绕不开破解那道加密。
03 — 卡点

厂商通道的加密

收发共用一套格式:report id 0x55,定长 64 字节,结构是「1 字节头 + 8 字节密文块 + 恒定填充块反复」。

// 设备心跳,每 ~10.1 秒一帧,内容恒定
55 9a e7 f3 05 32 03 f0 db 38 90 c4 99 a3 60 aa ad 38 90 c4 …
   └─ 数据块 ─┘             └─ 恒定填充,反复到底 ─┘

// App 下发的灯效帧(lldb 断 IOHIDDeviceSetReport 抓到)
55 4a c5 c6 12 01 88 4a 2d 38 90 c4 99 a3 60 aa ad …   ← 空闲轮询,重复数十次
55 24 56 9e f2 28 e1 45 a1 38 90 c4 99 a3 60 aa ad …
55 3c ea 0f c0 ad ec 89 47 38 90 c4 99 a3 60 aa ad …

已经推出来的性质

  • 64 位分组 ECB,静态密钥——恒定明文加出恒定密文(那个反复出现的填充块就是证据)。
  • 收发同一把密钥——两个方向的填充块字节完全一致。
  • 确定性——同一个键每次按,64 字节逐字节相同(隔 10 秒两次按,一模一样)。
  • 加密位置已定位——在 kwdm.dylib(Kehwin 厂商 SDK,体积小、可静态分析), 不在庞大的 Qt 主程序里。
  • 算法未在字符串层暴露;TEA/XTEA 的 0x9E3779B9 常量不存在。

抓包工具链(已跑通,可复用)

  • DYLD_INSERT_LIBRARIES 注入 失败——AMFI 记着 App 的公证出身, 重签 + 去硬化运行时都没用,连 __RESTRICT 段都没有也照样剥。
  • lldb Python 驱动 成功——断点打在 IOHIDDeviceSetReport / IOHIDDeviceGetReport,自动 dump 参数并续跑。输出帧就是这么拿到的。
后续:这道墙绕过去了,不用破。 顺着 lldb 抓到的调用栈往下查 kwdm.dylib,发现它根本不是内部库——见下一节。上面这些密码学性质现在只剩 参考价值(留给 v2 干净实现用)。

参数含义也是白送的

SDK 内嵌的回调选择器直接把每个字段命名了,不用猜:

onMessageDeviceLedEffect:mode:speed:bright:red:green:blue:
onMessageDeviceKeyEvent:index:status:physicalIndex:
onMessageDeviceBattery:battery:voltage:charging:chargeFull:lowbat:powerOff:

也就是说 setDeviceLedEffect 能设任意 RGB,按键事件带上了 按下/抬起和物理位号,电池是真值。另外 encrypt_data / decrypt_data 也在导出表里——v2 做干净实现时可以拿它当预言机。

代价说清楚:走 SDK 这条路,app 依赖你机器上装着 Ulanzi Studio (我们只加载它,绝不分发它的 dylib)。所以分两步:v1 用 SDK,功能今天就全通; v2 再用 SDK 当预言机反推协议,做成能独立分发的干净实现。
04 — 已排除

蓝牙这条路不存在

官方连不上蓝牙不是 bug,是这设备压根没有蓝牙。四条独立证据:

  • BLE 栈只服务另一个产品:libUlanziFZBle.dylib 里唯一的设备名过滤是 Ulanzi TC002(像素时钟),主程序里的发现类直接叫 Tc002Discovery。
  • AU05 是两段式硬件,固件分开 OTA:Dongle(AU05_USB) 是 USB 接收器, Mic(AU05_Device) 是手持端。
  • 无线段是 Nordic 2.4GHz 私有协议:主程序含 NRF~#P,配套 DongleSN / DongleVersion / DongleReboot / Paired。
  • 系统蓝牙已配对列表里没有它,device_source.json 的 MacAddress 恒为空。
这反而是好消息。 接收器同样以 USB HID 出现,所以有线直连和 2.4G 无线走的是 同一套 HID 代码,不用分两套,也不用碰蓝牙那边的 sendAuthMessage 鉴权握手。 实现提示:枚举时按 VID 0xFFF1 匹配、放宽 PID,因为接收器 PID 大概率与手持直连不同。

未做:实机 BLE 广播扫描。ad-hoc 签名的扫描工具被 macOS TCC 拒(连 centralManagerDidUpdateState 都不触发)。要 100% 确认,用手机 nRF Connect 扫一次即可。

daemon:让 hook 不拖慢 agent

每次 hook 都开一遍 SDK 要 2.7 秒——而 PreToolUse 是每次工具调用都触发的, 这个延迟直接不可用(官方也正因如此跑 ustudio-cli --singleton-server)。改成常驻:

vibekey serve 常驻,独占 SDK 与设备,听 $HOME/.vibekey.sock ▲ │ 一行文本:state working vibekey hook 写完就退出 —— 实测 0.01s
当前真实状态:代码链路已经端到端跑通了——daemon 起得来、hook 0.01s 投递、 状态正确解析,日志里如实报「丢弃(设备不在线)」。唯一缺的是把设备插回来。 在硬件验证之前,灯效这块仍应视为「已写完,未证实」。

07 — 下一步

按这个顺序推进

  1. 把设备插回来,标定灯效

    唯一的硬阻塞。设备一上线就跑 vibekey sdk 读回 getDeviceLedEffect 的当前值,确定 mode / speed / bright 的合法取值 (现在是命令行旋钮 --mode/--speed/--bright,默认值纯属猜测)。 然后 vibekey set-state working 应该让它变绿。

  2. 接通按键读取

    daemon 里监听 deviceKeyEvent 消息,解出 index / status / physicalIndex,交给 Mac App 里已经写好的 ShortcutRunner 注入。 ✕=Esc、侧边键自定义随即可用——注入那一半早就完成了。

  3. Mac App 换用 SDK

    把写死的 85% 换成 getDeviceBattery 真值;界面上的映射配置 通过 setDeviceButtonShortcutFunction 真正写进设备。

  4. daemon 常驻化

    vibekey serve 挂成 launchd 服务,开机自起、掉线自恢复。

  5. v2 干净实现 + 分发

    拿 SDK 当预言机反推协议后重写,摆脱依赖。CLI 走 Homebrew(零成本); Mac App 公证 DMG(需 99 美元/年开发者号)或 Homebrew cask。

08 — 边界

法律上站得住

为互操作性逆向自己买的硬件是受保护的:美国 DMCA §1201(f) 有明确的互操作例外, 欧盟软件指令 Art.6 同理。协议本身不受版权保护,自己写的客户端也不受限。

要守住的只有两条:

  • 不重新分发厂商的固件、图标等版权素材。
  • 不绕过付费授权(目前没发现有,插件市场是免费的)。
技术细节的完整记录在仓库的 PROTOCOL.md;逆向脚本(au05_sniff、 lldb 驱动 driver2.py)在会话 scratchpad,可复用。
